Eight build tasks split the P36 codebase — six analysis items, plus layout and database. All eight quietly pass through the same three shared files (config.py, metrics.py, prepare.py), and each task owns every other file that belongs to it exclusively — its page, its analysis module, and its own app/lib/<task>.py cached-data layer, so depending on one task's data never pulls in another task's code. P36 代码库拆成八个建设任务——六个 analysis 项目,加上排版和数据库。八个任务都会 经过同样的三个公共文件(config.py、metrics.py、 prepare.py),其它每个文件都完全专属于对应的任务——页面、分析模块， 以及各自的 app/lib/<任务>.py 缓存数据层——依赖某个任务的数据， 永远不会带进另一个任务的代码。

Cached data access is per-task, not shared. Each task's page and analysis module are backed by its own app/lib/<task>.py — seven independent files (one per active task, one per withdrawn one, plus Home's), each importing only the p36.analysis module(s) its own page actually needs. That's a deliberately different category from config.py/metrics.py/prepare.py above — those three are the stable definitions every task genuinely shares. app/lib/scenario_analysis.py is the one lib file that legitimately imports two other tasks' analysis modules — see its own docstring for why. 缓存数据层是按任务分的，不是共用的。每个任务的页面和分析模块背后都是 自己的 app/lib/<任务>.py——七个各自独立的文件（在用的每个 任务一个、下线的每个任务也一个、外加Home自己的），每个只import自己页面真正 需要的那个(或那些) p36.analysis 模块。这跟上面的 config.py/metrics.py/prepare.py 是刻意 不同的两类——那三个才是每个任务真正共用的稳定定义。 app/lib/scenario_analysis.py 是唯一一个合理地跨两个任务import的 lib文件——为什么见它自己的docstring。

Direct task-to-task imports任务之间的直接 import

No src/p36/analysis/*.py module imports another one — the only files any of them reach into are p36.config and p36.metrics, both part of the shared core above. FIELD_COLUMN_EXPLODED is read by Go8 Benchmarking, Journal Tier, and International Collaboration the same way any other p36.config constant is — a shared-core dependency, not a code dependency on Field Analysis's module. app/lib/scenario_analysis.py is the one file still allowed to know about more than one task's analysis module at a time, which is exactly its job — importing go8_benchmarking and journal_tier directly, an honest exception documented in its own docstring, not incidental coupling. src/p36/analysis/*.py 里没有任何一个模块 import 另一个——它们能伸进去的只有 p36.config 和 p36.metrics， 都是上面公共文件的一部分。FIELD_COLUMN_EXPLODED 被 Go8 Benchmarking、Journal Tier 和 International Collaboration 读取，跟读取任何其它 p36.config 常量一样——是一个公共文件层面的依赖，不是对 Field Analysis 模块的代码依赖。唯一还被允许同时知道多个任务的analysis模块的文件是 app/lib/scenario_analysis.py，而这正是它本来该做的事——直接 import 了 go8_benchmarking 和 journal_tier，是一个写在它自己 docstring里的坦白例外，不是意外的耦合。

Practical read for splitting the work: no analysis task is a build-order dependency for another one — none of them import each other, so all 6 can genuinely be built in parallel, right down to each task's own app/lib/<task>.py file. The one coordination point that's left is a shared-core one, same category as any other config.py constant: FIELD_COLUMN_EXPLODED's shape should still be agreed early, since Go8, Journal Tier, International Collaboration and Scenario all consume data shaped by it — but that's a conversation about a config value, not a code dependency on Field Analysis's module. Whoever builds Scenario Analysis is the one exception that still needs another task's pieces to exist first — app/lib/scenario_analysis.py's get_client_institution_scenario() and get_field_gap_closure_scenario() can't be wired up until Go8 Benchmarking's institution_partner_flag() and field_gap_vs_peers() exist. Database has no upward callers to coordinate with — its risk is entirely in the three config.py/metrics.py/prepare.py consumers below it moving before its schema settles. 分工时的实操提示：没有哪个分析任务是另一个任务的构建顺序依赖——它们 互相都不 import，6个可以真正并行开工，连各自的 app/lib/<任务>.py 文件都可以独立开工。剩下唯一要协调的是一个 公共文件层面的问题，跟任何其它 config.py 常量性质一样： FIELD_COLUMN_EXPLODED 的形状还是应该尽早定下来，因为 Go8、Journal Tier、International Collaboration 和 Scenario 都要用到按它整理出来的数据——但这是 在谈一个配置值，不是对 Field Analysis 模块的代码依赖。唯一还需要"等另一个任务的 东西先写好"的例外是负责 Scenario Analysis 的人—— app/lib/scenario_analysis.py 的 get_client_institution_scenario() 和 get_field_gap_closure_scenario() 得等 Go8 Benchmarking 的 institution_partner_flag() 和 field_gap_vs_peers() 先存在才能接起来。数据库任务没有上游要协调——它的风险全在于下面三个 config.py/metrics.py/prepare.py 的消费者会不会在它的schema定稳之前就先动了。
