Eight build tasks split the P36 codebase — six analysis items, plus layout and database. All eight quietly pass through the same four shared files (config.py, metrics.py, prepare.py, lib.py), and each task now lists every file that belongs to it exclusively — not just its page and its analysis module — plus, new in this revision, the exact import line behind every lit chip, so "Config: on" isn't a guess anyone has to go verify in the source. P36 代码库拆成八个建设任务——六个 analysis 项目,加上排版和数据库。八个任务都会 经过同样的四个公共文件(config.py、metrics.py、 prepare.py、lib.py),现在每个任务也列出了完全专属于它 的文件——不只是页面和分析模块这两个——本次修订新增的是,每一个点亮的 chip 背后具体的 import 那一行,这样"Config: 已用"就不再是一句 需要自己去源码里核实的猜测。

The shared core公共文件

Four files no single task owns outright — change one, and every task with a lit chip above needs a look before merging. Each item's Imports line is what that shared file itself pulls in — not who calls it, but what it depends on. 没有任何一个任务能独占的四个文件——改动其中一个,上面 chip 亮着的每个任务合并 前都得看一眼。每一项的Imports是这个公共文件自己依赖了什么——不是谁 调用它,而是它自己依赖谁。

Direct task-to-task imports任务之间的直接 import

Everything above went through the shared core. These five don't — one task's module reaches directly into another's. 上面都是经过公共文件的依赖。这五条不是——一个任务的模块直接伸进 另一个任务的模块。

direct Python import直接 import glued in lib.py, not a module import在 lib.py 拼接,不是模块 import

Practical read for splitting the work: whoever owns Field Analysis (3) is a dependency for whoever owns Go8 (1), Journal Tier (2), and International Collaboration (4) — land its FIELD_COLUMN_EXPLODED shape first. Whoever owns Scenario (6) is downstream of both Go8 and Journal Tier and should freeze its interface last. Database has no upward callers to coordinate with — its risk is entirely in the four config.py/metrics.py consumers below it moving before its schema settles. 分工时的实操提示:负责 Field Analysis(3)的人是负责 Go8(1)、Journal Tier(2)、International Collaboration(4)的人的上游——先把 FIELD_COLUMN_EXPLODED 的形状定下来。负责 Scenario(6)的人在 Go8 和 Journal Tier 下游,接口应该最后再定。数据库任务没有上游要协调——它的风险 全在于下面四个 config.py/metrics.py 的消费者会不会在 它的 schema 定稳之前就先动了。
