Eight build tasks split the P36 codebase — six analysis items, plus layout and database. All eight quietly pass through the same four shared files (config.py, metrics.py, prepare.py, lib.py), and each task now lists every file that belongs to it exclusively — not just its page and its analysis module — plus, new in this revision, the exact import line behind every lit chip, so "Config: on" isn't a guess anyone has to go verify in the source. P36 代码库拆成八个建设任务——六个 analysis 项目,加上排版和数据库。八个任务都会 经过同样的四个公共文件(config.py、metrics.py、 prepare.py、lib.py),现在每个任务也列出了完全专属于它 的文件——不只是页面和分析模块这两个——本次修订新增的是,每一个点亮的 chip 背后具体的 import 那一行,这样"Config: 已用"就不再是一句 需要自己去源码里核实的猜测。

Direct task-to-task imports — closed 2026-09-13任务之间的直接 import——2026-09-13清零

Until 2026-09-12 there were four — one task's module reaching directly into another's — plus one value passed cleanly through app/lib.py. Every one of the four is now gone: each was closed either by moving the shared thing into an actual shared-core file, or by having app/lib.py compute it and pass the result in as a plain function argument, the same pattern the fifth one already used. 直到2026-09-12为止，这里还有四条——一个任务的模块直接伸进另一个 任务的模块——外加一条是干净地经由 app/lib.py 传值的。现在这四条全部 关闭了：要么把共用的东西挪进了真正的公共文件，要么让 app/lib.py 自己 算好、把结果当普通函数参数传进去——用的正是第五条本来就在用的那种模式。

No p36.analysis.* module imports another one any more — the only files any of them reach into now are p36.config and p36.metrics, both already part of the shared core above. app/lib.py is the one place still allowed to know about more than one task at a time, which is exactly its job. p36.analysis.* 里没有任何一个模块还在 import 另一个了—— 现在它们能伸进去的只剩 p36.config 和 p36.metrics，都已经是 上面公共文件的一部分。唯一还被允许同时知道多个任务的地方是 app/lib.py， 而这正是它本来该做的事。

Practical read for splitting the work, updated for the 2026-09-13 decoupling: no analysis task is a build-order dependency for another one any more — none of them import each other, so all 6 can genuinely be built in parallel. The one coordination point that's left is a shared-core one, same category as any other config.py constant: FIELD_COLUMN_EXPLODED's shape should still be agreed early, since Go8, Journal Tier, International Collaboration and Scenario all consume data shaped by it — but that's a conversation about a config value, not a code dependency on Field Analysis's module. Whoever builds app/lib.py's integration layer (not a task of its own) is the one place that does still need every task's functions to exist first — get_client_institution_scenario() and get_field_gap_closure_scenario() can't be wired up until both Go8 Benchmarking and Scenario Analysis's own pieces are done. Database has no upward callers to coordinate with — its risk is entirely in the four config.py/metrics.py consumers below it moving before its schema settles. 分工时的实操提示，2026-09-13解耦之后更新：现在没有哪个分析任务是另一个 任务的构建顺序依赖了——它们互相都不 import，6个可以真正并行开工。剩下唯一要协调 的是一个公共文件层面的问题，跟任何其它 config.py 常量性质一样： FIELD_COLUMN_EXPLODED 的形状还是应该尽早定下来，因为 Go8、Journal Tier、International Collaboration 和 Scenario 都要用到按它整理出来的数据——但这是 在谈一个配置值，不是对 Field Analysis 模块的代码依赖。唯一还需要"等所有任务的 函数都写好"的地方是负责搭 app/lib.py 集成层的人（这不是一个独立任务） ——get_client_institution_scenario() 和 get_field_gap_closure_scenario() 得等 Go8 Benchmarking 和 Scenario Analysis 各自的部分都写完才能接起来。数据库任务没有上游要协调——它的风险全在于 下面四个 config.py/metrics.py 的消费者会不会在它的 schema 定稳之前就先动了。
