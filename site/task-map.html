Eight build tasks split the P36 codebase — six analysis items, plus layout and database. All eight quietly pass through the same three shared files (config.py, metrics.py, prepare.py), and each task lists every file that belongs to it exclusively — not just its page and its analysis module. Updated 2026-09-13: the old shared app/lib.py (one file, imported by every page) is gone — split into one app/lib/<task>.py per task, so a task's cached-data layer is now something it owns outright, not a file six other pages could also be touching. P36 代码库拆成八个建设任务——六个 analysis 项目,加上排版和数据库。八个任务都会 经过同样的三个公共文件(config.py、metrics.py、 prepare.py),现在每个任务也列出了完全专属于它的文件——不只是页面 和分析模块这两个。2026-09-13更新：原来共用的 app/lib.py（一个 文件、被每个页面 import）已经拆掉——换成每个任务各自一个 app/lib/<任务>.py，这样一个任务的缓存数据层就是它自己完全 拥有的东西，不再是六个别的页面也可能同时在改的文件。

The shared core公共文件

Three files no single task owns outright — change one, and every task with a lit chip above needs a look before merging. Each item's Imports line is what that shared file itself pulls in — not who calls it, but what it depends on. lib.py used to be a fourth — see the task cards above and the callout below for where it went on 2026-09-13. 没有任何一个任务能独占的三个文件——改动其中一个,上面 chip 亮着的每个任务合并 前都得看一眼。每一项的Imports是这个公共文件自己依赖了什么——不是谁 调用它,而是它自己依赖谁。lib.py 以前是第四个——去哪了见上面的 任务卡片和下面的说明（2026-09-13）。

Where lib.py went (2026-09-13): it was never really a "shared core" file the way config.py/metrics.py/ prepare.py are — those three are stable definitions every task reads; lib.py was one big file every page's own caching code happened to live inside, which meant depending on it for one function pulled in all six analysis modules' imports too. It's now app/lib/<task>.py — seven independent files (one per active task, one per withdrawn one, plus Home's), each importing only the p36.analysis module(s) its own page actually needs. See each task card above for its own file, and app/lib/scenario_analysis.py's own docstring for the one place a lib file still legitimately imports two other tasks' analysis modules. lib.py 去哪了（2026-09-13）：它其实从来不是真正意义上的 "公共文件"，不像 config.py/metrics.py/prepare.py 这三个——那三个是每个任务都会读取的稳定定义；lib.py 只是恰好每个 页面自己的缓存代码都写在同一个大文件里，这意味着只依赖其中一个函数，也会把 六个分析模块的import全部带进来。现在它变成了 app/lib/<任务>.py——七个各自独立的文件（在用的每个任务一个、 下线的每个任务也一个、外加Home自己的），每个只import自己页面真正需要的那个 (或那些) p36.analysis 模块。每个任务自己的文件见上面对应的任务 卡片，唯一一处lib文件仍然合理地跨两个任务import的地方，见 app/lib/scenario_analysis.py 自己的docstring。

Direct task-to-task imports — closed 2026-09-13任务之间的直接 import——2026-09-13清零

Until 2026-09-12 there were four — one task's module reaching directly into another's — plus one value passed cleanly through the shared lib layer (at the time, still one file, app/lib.py). Every one of the four is now gone: each was closed either by moving the shared thing into an actual shared-core file, or by having the lib layer compute it and pass the result in as a plain function argument, the same pattern the fifth one already used. That lib layer was itself split into app/lib/<task>.py later the same day — the table below already names the current file, app/lib/scenario_analysis.py. 直到2026-09-12为止，这里还有四条——一个任务的模块直接伸进另一个 任务的模块——外加一条是干净地经由共用的lib层传值的（当时还是一个文件， app/lib.py）。现在这四条全部关闭了：要么把共用的东西挪进了真正的 公共文件，要么让lib层自己算好、把结果当普通函数参数传进去——用的正是第五条本来 就在用的那种模式。这个lib层本身在同一天晚些时候又被拆成了 app/lib/<任务>.py——下表里已经写的是现在的文件名 app/lib/scenario_analysis.py。

No src/p36/analysis/*.py module imports another one any more — the only files any of them reach into now are p36.config and p36.metrics, both already part of the shared core above. app/lib/scenario_analysis.py is the one file still allowed to know about more than one task's analysis module at a time, which is exactly its job — see its own docstring for why that's an honest exception, not incidental coupling. src/p36/analysis/*.py 里没有任何一个模块还在 import 另一个了——现在它们能伸进去的只剩 p36.config 和 p36.metrics， 都已经是上面公共文件的一部分。唯一还被允许同时知道多个任务的analysis模块的文件是 app/lib/scenario_analysis.py，而这正是它本来该做的事——为什么这是一个 坦白的例外而不是意外的耦合，见它自己的docstring。

Practical read for splitting the work, updated for the 2026-09-13 decoupling and lib split: no analysis task is a build-order dependency for another one any more — none of them import each other, so all 6 can genuinely be built in parallel, right down to each task's own app/lib/<task>.py file. The one coordination point that's left is a shared-core one, same category as any other config.py constant: FIELD_COLUMN_EXPLODED's shape should still be agreed early, since Go8, Journal Tier, International Collaboration and Scenario all consume data shaped by it — but that's a conversation about a config value, not a code dependency on Field Analysis's module. Whoever builds Scenario Analysis is the one exception that still needs another task's pieces to exist first — app/lib/scenario_analysis.py's get_client_institution_scenario() and get_field_gap_closure_scenario() can't be wired up until Go8 Benchmarking's institution_partner_flag() and field_gap_vs_peers() exist. Database has no upward callers to coordinate with — its risk is entirely in the three config.py/metrics.py/prepare.py consumers below it moving before its schema settles. 分工时的实操提示，2026-09-13解耦+lib拆分之后更新：现在没有哪个分析任务是 另一个任务的构建顺序依赖了——它们互相都不 import，6个可以真正并行开工，连各自的 app/lib/<任务>.py 文件都可以独立开工。剩下唯一要协调的是一个 公共文件层面的问题，跟任何其它 config.py 常量性质一样： FIELD_COLUMN_EXPLODED 的形状还是应该尽早定下来，因为 Go8、Journal Tier、International Collaboration 和 Scenario 都要用到按它整理出来的数据——但这是 在谈一个配置值，不是对 Field Analysis 模块的代码依赖。唯一还需要"等另一个任务的 东西先写好"的例外是负责 Scenario Analysis 的人—— app/lib/scenario_analysis.py 的 get_client_institution_scenario() 和 get_field_gap_closure_scenario() 得等 Go8 Benchmarking 的 institution_partner_flag() 和 field_gap_vs_peers() 先存在才能接起来。数据库任务没有上游要协调——它的风险全在于下面三个 config.py/metrics.py/prepare.py 的消费者会不会在它的schema定稳之前就先动了。
