Sub-Question Navigation Close-Reading子问题跳转机制精读

Every platform page opens with a "Sub-questions this page answers" panel, and every question in it that has somewhere to go is a live link — click it and the page smooth-scrolls to the exact chart, on the same page or, if the honest answer lives elsewhere, on a different one entirely. This note takes that one feature apart in full: the two-layer data model behind it, the same-page jump (pure CSS, zero JS), and the cross-page jump (a genuinely non-trivial trick using st.iframe to escape Streamlit's own sandbox). 平台每个页面开头都有一个"本页回答的子问题"面板，面板里凡是有地方可去的 问题都是一个真正能点的链接——点一下，页面会平滑滚动到具体那张图，可能是本页内，也可能 是——如果诚实的答案在别处——完全跳到另一个页面。这份笔记把这一个功能彻底拆开讲：背后 两层的数据模型、同页跳转（纯CSS，零JS）、以及跨页跳转（一个真正有技术含量的技巧， 用st.iframe逃出Streamlit自己的沙箱）。

01

Two Layers两层结构

README.md · app/pages/*.py · app/theme.py

"Question and sub-question navigation" is really two separate, independent layers stacked on top of each other — worth naming clearly before diving into code, because the two use completely different mechanisms. "问题和子问题的导向"其实是两层完全独立、叠在一起的东西——先把两层 分清楚再看代码，因为两层用的是完全不同的机制。

1 Item → page大问题 → 页面 Static, one-to-one, decided at file-creation time. README Analysis item 16 is app/pages/1_Go8_Benchmarking.py — theme.header(title, caption, ...) just states this in the caption text. No navigation logic here at all. 静态的、一对一的，文件建立的时候就定死了。README第16项就是 app/pages/1_Go8_Benchmarking.py——theme.header(title, caption, ...) 只是把这个事实写在说明文字里。这一层完全没有导航逻辑。
2 Sub-question → chart子问题 → 图表 Dynamic, many-to-one or many-to-many, and this is the layer with actual click-to-jump behaviour — built entirely by theme.question_panel(), theme.anchor(), and theme._cross_page_scroll_bridge(), the subject of the rest of this note. 动态的、多对一或多对多，也是真正带"点击跳转"行为的一层——完全由 theme.question_panel()、theme.anchor()、 theme._cross_page_scroll_bridge()三个函数搭起来的，是这份笔记 接下来全部内容的主题。

The four states a sub-question can be in — and only the first two ever carry a link that goes somewhere on this platform, "elsewhere" links off to a different page, "open" has nowhere to go at all: 子问题可能处于的四种状态——只有前两种会带一个真正指向这个平台内部 某处的链接，"elsewhere"是链接到另一个页面，"open"则完全没有地方可跳：

✓doneanswered directly below — same-page link本页直接回答——同页链接
~partialaggregate/qualitative only — usually still same-page只是聚合/定性层面——通常也是同页链接
→elsewhereanswered on a different page — cross-page link在其它页面回答——跨页链接
?opennot built anywhere — plain text, no link平台尚未实现——纯文字，没有链接

question_panel() Taken Apartquestion_panel() 拆解

app/theme.py

The function every page calls once, right after theme.header(), with a list describing every sub-question the page's brief item includes. 每个页面在theme.header()之后立刻调用一次的函数，传入一份列表，描述这一页对应的brief条目里的每一个子问题。

Input shape输入的数据形状
theme.question_panel([
    ("Do Q1 publications receive more citations than Q2, Q3 or Q4?", "done", "jt-quartile"),
    ("Which faculties/fields have the highest success rates in Q1 publishing?",
     "elsewhere", "/Field_Analysis#fa-q1-share"),
    ("Are particular publication strategies more successful in some fields?", "open"),  # 2-tuple: no anchor2元组：没有锚点
])
  • A list of tuples, each 2 or 3 elements: (question_text, status) or (question_text, status, anchor_id). The third element decides everything about click behaviour — omit it (a bare 2-tuple, typically an "open" item, or a "partial" answered by a synthesis of several sections) and the question renders as plain, non-clickable text.一份元组列表，每个元组2个或3个元素：(问题文字, 状态)或 (问题文字, 状态, 锚点id)。第三个元素决定了点击行为的一切——省略它 （2元组，通常是"open"状态，或者是靠综合几个部分回答的"partial"），问题就渲染成 普通、不可点的文字。
  • "jt-quartile" — a bare id, no leading slash: same-page jump."jt-quartile"——不带斜杠的裸id：同页跳转。
  • "/Field_Analysis#fa-q1-share" — starts with /: cross-page jump, to another page's own anchor."/Field_Analysis#fa-q1-share"——以/开头：跨页跳转，跳到另一个页面自己的锚点。
The unpacking trick解包技巧
for item in items:
    question, status, anchor_id = (*item, None)[:3]
    icon, bg, fg = _STATUS_STYLE[status]
    if anchor_id:
        href = anchor_id if anchor_id.startswith("/") else f"#{anchor_id}"
        question_html = f'<a href="{href}" class="qjump">{question}</a>'
    else:
        question_html = question
  • (*item, None)[:3]: worth unpacking slowly. *item spreads the tuple (2 or 3 elements) into individual values; appending one None guarantees at least 3 values are now available; [:3] keeps only the first 3. Whether the caller wrote 2 or 3 elements, anchor_id ends up either the real anchor string or None — no if len(item) == 3 branch needed anywhere.(*item, None)[:3]：值得慢慢拆开看。*item把元组 （2或3个元素）展开成单个值；后面补一个None，保证至少有3个值可用； [:3]只保留前3个。不管调用方写的是2个还是3个元素， anchor_id最后要么是真的锚点字符串，要么是None—— 任何地方都不需要写if len(item) == 3这种判断。
  • _STATUS_STYLE[status]: a plain dict lookup — keys are the 4 status strings, values a 3-tuple (icon, background, foreground) — swapping a long if/elif chain for one dict access._STATUS_STYLE[status]：一次普通的字典查找——key是4个状态字符串， value是三元组(图标, 背景色, 前景色)——用一次字典访问代替了一长串 if/elif。
  • href = anchor_id if anchor_id.startswith("/") else f"#{anchor_id}": the entire routing decision for "same page or different page" is this one line — a leading / is treated as a real URL path (Streamlit's own page routing understands it), anything else gets an # prepended and becomes a same-page fragment.href = anchor_id if anchor_id.startswith("/") else f"#{anchor_id}"： "跳本页还是跳别的页"这整个路由判断就是这一行——带前导/的当成真正的URL 路径处理（Streamlit自己的页面路由认得），其它情况前面补一个#变成同页 片段。
  • The generated <a href="..." class="qjump"> is a completely ordinary anchor tag — every bit of the click behaviour that follows is the browser and (for cross-page links) the bridge component reacting to a normal link, not any special widget or callback.生成出来的<a href="..." class="qjump">是一个完全普通的 锚点标签——接下来所有的点击行为，都是浏览器（以及跨页链接情况下的桥接组件）对一个 普通链接做出的反应，不是什么特殊组件或回调函数。
Styling, not routing这是样式，不是路由 class="qjump" only exists so inject()'s CSS (a.qjump { border-bottom: 1.5px dashed ... }) can give clickable questions a dashed underline that turns solid blue on hover — visually marking "this one goes somewhere" versus the plain-text "open" items sitting right next to it in the same panel. class="qjump"存在的唯一理由是让inject()里的CSS （a.qjump { border-bottom: 1.5px dashed ... }）能给可点击的问题加一条 虚线下划线、悬停变实心蓝色——用视觉上标出"这一条能点"，跟同一个面板里紧挨着的 纯文字"open"条目区分开。
03

anchor() and the Same-Page Jumpanchor() 与同页跳转

app/theme.py

The landing side of a same-page link — an invisible marker placed exactly where a jump should land. 同页链接的"落点"那一侧——一个放在跳转该落地的精确位置上的、看不见的标记。 

def anchor(anchor_id: str) -> None:
    st.markdown(f'<div id="{anchor_id}" class="qanchor"></div>', unsafe_allow_html=True)
  • Called right above the st.subheader(...) a question should land on — e.g. theme.anchor("fa-q1-share") then st.subheader("Q1 share by field") immediately after, on the Field Analysis page.调用位置紧挨在某个问题该落地的st.subheader(...)正上方——比如 Field Analysis页面里theme.anchor("fa-q1-share")紧接着就是 st.subheader("Q1 share by field")。
  • This is where the browser's completely native anchor-jump behaviour takes over: any <a href="#some-id">, clicked anywhere on the page, makes the browser scroll to the element with id="some-id" — a feature of HTML itself, decades old, nothing Streamlit- or Python-specific about it.这里靠的是浏览器完全原生的锚点跳转行为：任何一个 <a href="#some-id">，在页面任何地方被点击，浏览器都会自动滚动到 id="some-id"的元素——这是HTML本身的功能，存在了几十年，跟Streamlit或 Python完全没关系。
  • scroll-margin-top: 90px (set on .qanchor in inject()'s injected CSS) is the one piece of styling this needs: without it, the anchor would land exactly at the very top of the viewport, tucked directly under Streamlit's own sticky header — the extra margin leaves room for that header not to cover the landing spot.scroll-margin-top: 90px（在inject()注入的CSS里，加在 .qanchor上）是唯一需要的样式补丁：没有它，锚点会正好落在视口最顶部， 直接被Streamlit自己的粘性顶栏挡住——这个额外的边距留出空间，让顶栏不会盖住落点。
  • html { scroll-behavior: smooth; } (also in inject()) is what turns the jump from an instant snap into a smooth scroll — a one-line, page-wide CSS switch, no JavaScript involved anywhere in this same-page path.html { scroll-behavior: smooth; }（同样在inject()里） 是让跳转从"瞬间跳过去"变成"平滑滚动过去"的开关——一行、全页生效的CSS，同页跳转这条 路径上完全没有涉及任何JavaScript。

The Cross-Page Bridge, in Full跨页跳转桥完整拆解

app/theme.py — _cross_page_scroll_bridge()

The part of this feature that's genuinely non-trivial — same-page anchors are a browser default; making a click land on a specific chart on a different Streamlit page needed solving from scratch. 这个功能里真正有技术含量的部分——同页锚点是浏览器自带的默认行为；让点击落在 另一个Streamlit页面的具体某张图上，是需要从头解决的问题。

Why the same trick doesn't just carry over为什么同一套技巧不能直接照搬
  • Problem 1 — timing. When the browser follows a link like /Field_Analysis#fa-q1-share, it tries to jump to #fa-q1-share the instant the new page's HTML is parsed. But Streamlit doesn't render a whole page at once — it streams elements in one by one over a WebSocket as the script runs. At the moment the browser tries to jump, the target <div id="fa-q1-share"> very likely doesn't exist in the DOM yet, so the native jump silently does nothing and is never retried.问题一——时机。浏览器跟随/Field_Analysis#fa-q1-share这样的链接时， 会在新页面HTML刚解析完的那一刻就尝试跳到#fa-q1-share。但Streamlit不是 一次性渲染整个页面的——它是在脚本运行的过程中，通过WebSocket把元素一个个"流"进来的。 浏览器尝试跳转的那一刻，目标<div id="fa-q1-share">很可能压根还不 存在于DOM里，于是原生跳转悄悄什么也不做，而且不会重试。
  • Problem 2 — no script execution. The obvious fix would be "wait for the element, then scroll to it with JavaScript" — but st.markdown(html, unsafe_allow_html=True) inserts its HTML through a code path in Streamlit's frontend that does not execute any embedded <script> tag. A hand-written retry loop dropped into a markdown string simply never runs.问题二——脚本不会执行。显而易见的修法是"等元素出现，再用JavaScript滚过去"—— 但st.markdown(html, unsafe_allow_html=True)插入HTML走的是Streamlit 前端的一条代码路径，这条路径不会执行任何插进去的<script>标签。 手写一个重试循环塞进markdown字符串里，根本不会被执行。
The escape hatch: st.iframe逃生舱口：st.iframe st.iframe(html_string, height=1) renders a genuine <iframe> element, and unlike st.markdown's HTML injection path, the browser treats an iframe's content as a real, independent document — its <script> tags execute normally. Because the iframe is served from the same origin as the main Streamlit app, it isn't sandboxed away from it: code running inside the iframe can reach window.parent and manipulate the actual page — not the 1-pixel-tall iframe itself. st.iframe(html_string, height=1)渲染出的是一个真正的 <iframe>元素，跟st.markdown插入HTML的那条路径不同， 浏览器把iframe里的内容当成一个真正独立的文档——里面的<script> 标签会正常执行。因为这个iframe跟主Streamlit应用同源，不会被沙箱隔离开：iframe内部 跑的代码能拿到window.parent，操作真正的页面——不是这个高度只有 1像素的iframe自己。
_cross_page_scroll_bridge()

Called once, unconditionally, at the end of every page's inject() — because any page might be the target of a cross-page link, every page needs to be ready to receive one.在每个页面的inject()末尾无条件调用一次——因为任何页面都可能是 跨页链接的目标，所以每个页面都得随时准备好接收一次跳转。

st.iframe(
    """
    <script>
    (function () {
        try {
            var hash = window.parent.location.hash;
            if (!hash || window.parent.__qjumpLastHash === hash) return;
            var id = decodeURIComponent(hash.slice(1));
            var attemptsLeft = 30;
            (function tryScroll() {
                var el = window.parent.document.getElementById(id);
                if (el) {
                    el.scrollIntoView({behavior: "smooth", block: "start"});
                    window.parent.__qjumpLastHash = hash;
                } else if (attemptsLeft > 0) {
                    attemptsLeft -= 1;
                    setTimeout(tryScroll, 200);
                }
            })();
        } catch (e) {}
    })();
    </script>
    """,
    height=1,  # st.iframe requires a positive integer — this component has no visible contentst.iframe要求正整数——这个组件没有可见内容
)
  • window.parent.location.hash: reads the URL fragment (#fa-q1-share) off the real page — window.parent, not window, is the whole trick; called without it, this would read the iframe's own (blank) location instead.window.parent.location.hash：从真正的页面上读取URL片段 （#fa-q1-share）——用window.parent而不是window 正是整个技巧的关键；不加这个，读到的会是iframe自己那个(空白的)location。
  • window.parent.__qjumpLastHash === hash: the de-dupe guard. This component remounts on every Streamlit rerun (every widget interaction re-executes the whole page script, including the inject() call), but window.parent itself persists across reruns — so a value stashed there survives even though the component that wrote it gets torn down and rebuilt. Without this check, clicking any unrelated button elsewhere on the target page would silently yank the view back to the same anchor every single time.window.parent.__qjumpLastHash === hash：去重防护。这个组件每次 Streamlit重跑都会重新挂载（每次控件交互都会重新执行整个页面脚本，包括 inject()那次调用），但window.parent本身在多次重跑之间是 持续存在的——所以存在它上面的值，即便写入它的那个组件被拆掉重建了，也依然留着。 没有这个检查，点一下目标页面上任何一个不相关的按钮，都会每次都悄悄把视图拽回同一个 锚点。
  • The tryScroll() polling loop: checks for the target element every 200ms, up to 30 times (6 seconds total) — this is the direct fix for Problem 1 above, giving Streamlit's own streamed rendering time to catch up before giving up.tryScroll()轮询循环：每200毫秒检查一次目标元素是否出现，最多试30次 （总共6秒）——这是对上面"问题一"最直接的修法，给Streamlit自己的流式渲染留出追上来 的时间，再放弃。
  • el.scrollIntoView({behavior: "smooth", block: "start"}): a browser-native DOM method, the JS equivalent of the same-page path's CSS scroll-behavior: smooth — block: "start" aligns the element to the top of the viewport rather than centring it.el.scrollIntoView({behavior: "smooth", block: "start"})：浏览器 原生的DOM方法，是同页跳转那条路径里CSS scroll-behavior: smooth的JS 等价物——block: "start"让元素对齐到视口顶部，而不是居中。
  • try { ... } catch (e) {}: swallows any error silently — this is a nice-to-have UX enhancement, not core functionality; if window.parent access ever throws (e.g. a stricter embedding context), the page should simply not scroll, never show a broken error to the user.try { ... } catch (e) {}：静默吞掉任何错误——这是一个锦上添花的 体验增强，不是核心功能；如果window.parent访问哪天抛出了异常（比如更 严格的嵌入环境），页面应该只是不滚动而已，绝不该给用户看一个报错。
  • height=1: st.iframe requires a positive integer height (height=0 raises StreamlitInvalidHeightError) — this component renders no visible content, so 1 pixel is the practical minimum.height=1：st.iframe要求高度是正整数 （height=0会报StreamlitInvalidHeightError）——这个组件 没有任何可见内容，所以1像素是实际能用的最小值。

Worked Example: One Click, Traced End to End完整实例：一次点击的全过程追踪

On the Journal Tier page, "Which faculties/fields have the highest success rates in Q1 publishing?" is marked elsewhere, pointing at "/Field_Analysis#fa-q1-share". Here's exactly what happens between the click and the screen settling on the right chart. 在Journal Tier页面，"哪些院系/学科的Q1成功率最高？"这个问题标的是 elsewhere，指向"/Field_Analysis#fa-q1-share"。下面是从 点击到画面最终停在正确图表上，中间具体发生的每一步。

  1. Render: question_panel() on the Journal Tier page sees a 3-tuple whose anchor starts with /, so it builds <a href="/Field_Analysis#fa-q1-share" class="qjump">...</a> — an ordinary link, styled with a dashed underline.渲染：Journal Tier页面的question_panel()看到一个锚点以 /开头的3元组，于是拼出<a href="/Field_Analysis#fa-q1-share" class="qjump">...</a>——一个普通链接，样式是虚线下划线。
  2. Click: the browser follows the link. Streamlit intercepts this internally as a request to switch to its Field_Analysis page (the multipage routing convention covered in the Dashboard & Charting note), carrying the #fa-q1-share fragment along in the URL.点击：浏览器跟随这个链接。Streamlit内部把它拦截成"切换到 Field_Analysis页面"的请求（多页路由的约定，见"看板与图表精读"），URL里 的#fa-q1-share片段也一起带过去。
  3. New page starts rendering: Field Analysis's script begins executing top to bottom. Its own theme.inject() call mounts a fresh copy of the bridge iframe — this instance has no memory of anything from before, since the whole component just remounted.新页面开始渲染：Field Analysis的脚本从头到尾开始执行。它自己的 theme.inject()调用挂载了一份全新的桥接iframe——这一份对之前发生的任何 事都没有记忆，因为整个组件刚刚重新挂载。
  4. Bridge reads the hash: inside the iframe, JS reads window.parent.location.hash → "#fa-q1-share". It's non-empty and doesn't match window.parent.__qjumpLastHash (nothing set it yet on this page load), so it proceeds.桥接组件读取hash：iframe内部，JS读取 window.parent.location.hash → "#fa-q1-share"。非空， 也不等于window.parent.__qjumpLastHash（这次页面加载还没人设过这个值）， 于是继续往下走。
  5. Polling: at this instant, <div id="fa-q1-share"> may or may not exist yet, depending on how far Field Analysis's script has streamed in. The loop tries getElementById, and if it's not there yet, waits 200ms and tries again — for up to 30 attempts.轮询：这一刻，<div id="fa-q1-share">存不存在，取决于 Field Analysis的脚本流式渲染到哪一步了。循环调用getElementById，如果 还没出现，等200毫秒再试一次——最多试30次。
  6. Found: once theme.anchor("fa-q1-share") has rendered (placed directly above the "Q1 share by field" st.subheader()), getElementById succeeds, the loop calls scrollIntoView, and the browser smooth-scrolls the real page — the same native mechanism the same-page path uses, just triggered from JS instead of a plain link click.找到了：一旦theme.anchor("fa-q1-share")渲染出来了 （放在"Q1 share by field"这个st.subheader()正上方）， getElementById成功，循环调用scrollIntoView，浏览器平滑 滚动真正的页面——用的是同页跳转那条路径同样的原生机制，只是这次是由JS触发的， 不是靠一次普通的链接点击。
  7. Guard set: window.parent.__qjumpLastHash = "#fa-q1-share" is recorded. If the user now clicks a dropdown or slider elsewhere on Field Analysis, the page reruns, the bridge remounts, reads the same hash again — and this time exits immediately at step 4, leaving the view exactly where the user scrolled it.设置防护：记录下window.parent.__qjumpLastHash = "#fa-q1-share"。 如果用户现在在Field Analysis页面上点了别的下拉框或滑块，页面重跑，桥接组件重新挂载， 再次读到同一个hash——这次会在第4步就直接退出，视图保持在用户当前滚动到的位置不变。

Technique Cheat Sheet技术点速查表

Native anchor jump #id原生锚点跳转 #id
Built into HTML itself — any link to #some-id makes the browser scroll to the element with that id, no JS required. Only works reliably when the target already exists in the DOM.HTML自带的功能——任何指向#some-id的链接，都会让浏览器滚动到那个id的元素，不需要JS。只有目标已经存在于DOM里时才能可靠工作。
scroll-behavior: smooth
A one-line, page-wide CSS switch turning every native jump (anchor click or JS scrollIntoView) from an instant snap into an animated scroll.一行全页生效的CSS开关，把每一次原生跳转（点锚点链接或JS调用scrollIntoView）从瞬间跳变改成带动画的平滑滚动。
scroll-margin-top
Reserves space above an anchor target so a page's own sticky header doesn't cover it after a jump — the CSS-only fix for "landed exactly under the toolbar."在锚点目标上方预留空间，避免跳转后被页面自己的粘性顶栏挡住——纯CSS修复"正好落在工具栏下面"的问题。
st.markdown(html, unsafe_allow_html=True)
Injects arbitrary HTML/CSS into a Streamlit page — but not <script> execution, which is exactly why this path alone can't build a cross-page jump.往Streamlit页面里注入任意HTML/CSS——但不会执行<script>，这正是单靠这条路径没法实现跨页跳转的原因。
st.iframe(html, height=n)
Renders a real, script-executing <iframe>, same-origin with the main app — the escape hatch that lets injected JS actually run.渲染一个真正会执行脚本的<iframe>，跟主应用同源——让注入的JS真正能跑起来的逃生舱口。
window.parent
From inside a same-origin iframe, a reference to the actual outer page — the difference between manipulating the invisible iframe itself and manipulating the real, visible document.在同源iframe内部，指向外层真正页面的引用——是操作那个看不见的iframe自己、还是操作真正可见文档，这两者的差别就在这一个引用上。
Polling with setTimeout
Repeatedly checking for a condition (here, "does this element exist yet") on a timer, with a maximum attempt count — a standard pattern for "wait for something that will eventually appear, but might not be ready right now."用定时器反复检查某个条件（这里是"这个元素出现了没有"），并设一个最多尝试次数——是"等待一个终将出现、但现在可能还没准备好的东西"的标准写法。
De-dupe guard via a persisted flag用一个持续存在的标记做去重
Stashing "the last hash already handled" on an object that survives across Streamlit reruns (window.parent), even though the component writing to it gets torn down and rebuilt every rerun.把"上一次已经处理过的hash"存在一个跨Streamlit重跑依然存在的对象上（window.parent），哪怕写入它的那个组件每次重跑都会被拆掉重建。
Tuple unpacking with a spread + slice展开+切片的元组解包
(*item, None)[:3] — pads a variable-length tuple out to a fixed length before unpacking, avoiding a manual length check.(*item, None)[:3]——在解包前把一个长度不固定的元组补齐到固定长度，避免手写长度判断。
el.scrollIntoView(options)
The JS/DOM method equivalent of a native anchor jump — {behavior:"smooth", block:"start"} animates the scroll and aligns the element to the top of the viewport.JS/DOM方法版本的原生锚点跳转——{behavior:"smooth", block:"start"}让滚动带动画，并把元素对齐到视口顶部。
